## Your agent doesn't know your libraries

Without help, an agent in your project guesses how your libraries work, or it remembers an older version. Today the fix is manual:

- Teams paste rules into `AGENTS.md`, and the rules drift away from the code.
- A library can put docs in its package, but nothing points the agent at them.
- Each agent reads its own files: `CLAUDE.md` and `.claude/` for Claude Code, `.codex/` for Codex.
- A library that builds on another one copies the upstream rules, and the copies go stale.

## How it works

A library writes its harness once, and every project that installs the library gets it.

## What your agent sees

Your agent gets short, current instructions, and you can trace each one to its source.

The examples on this site use one app. It depends on `@acme/ui`, a design system built on `@acme/colors` and `@acme/styles`. The packages are made up, and the output is real.

Each rule, docs index or script is a **unit** with an ID, such as `acme-colors:rules/usage`. The managed block that harnesspm writes into `AGENTS.md` names the unit behind every line:

<ManagedBlock marks={{ '#### Where colors come from': 'patched by acme-ui' }} />

The app depends only on `@acme/ui`. `@acme/colors` comes through it, and a patch from `@acme/ui` rewrites the first section of its rule for apps on `@acme/ui`. Lines marked `…` are cut here.

Docs are one pointer line each, and skills load when needed, so the always-on text stays small. `npx harnesspm status` shows its size.

## Upgrade the package, upgrade the rules

Your agent's knowledge of a library updates when the library does. Rules, docs and tools come from the version in `node_modules`. Nothing is copied, so nothing drifts. The managed block and the lock are committed, so the pull request shows what changed. Here is an upgrade of `@acme/ui` from 4.2.0 to 4.3.0, which changed only its `tokens` script, so only the lock changed:

## Libraries pass on what they build on

A library passes on the harness of the libraries it builds on, adapted for its users. `@acme/ui` does this with two fields in its `harness/plugin.json`:

```json
"extensions": {
  "dev.harnesspm": {
    "extends": ["@acme/colors", "@acme/styles"],
    "patch": {
      "acme-colors:rules/usage": "./dev.harnesspm/patches/acme-colors-usage.patch.md"
    }
  }
}
```

- `extends` gives every app on `@acme/ui` the harness of both packages, in the versions that `@acme/ui` uses.
- `patch` changes one section of the colors rule and keeps the rest.

So an app that installs only `@acme/ui` gets the rules, docs, skills and tools of all three packages.

## One source for Claude Code and Codex

You keep one copy of each instruction, not one per agent. Write a rule, skill, sub-agent or hook once. Each agent gets it in its own files: the managed block in `AGENTS.md` for both, `.claude/` for Claude Code, `.codex/` and `.agents/skills/` for Codex. Other agents that read `AGENTS.md` and `.agents/skills/` get the portable parts. See [every file harnesspm writes](https://github.com/tenphi/harnesspm/blob/main/docs/spec/04-outputs.md).

This works before any library ships a harness:

- **Your project.** `npx harnesspm new rule usage` starts a `harness/` folder in your repository.
- **All your repositories.** Publish shared rules as a harness-only package, and add it as a dev dependency in each.

## You decide what applies and what runs

Your project has the last word on every unit. One `harnesspm.json` holds your changes and your trust:

```json
{
  "patch": {
    "acme-colors:rules/usage": "./harnesspm/patches/acme-colors-usage.patch.md"
  },
  "exclude": ["acme-styles:hooks/check-edit"],
  "trust": {
    "@acme/ui": true,
    "@acme/styles": true,
    "@acme/colors": "pin"
  }
}
```

- A **patch** changes one section of a rule and keeps the rest. When an upgrade changes that section, `sync` warns you. **exclude** drops a unit or a whole package. **replace** swaps a unit for your own file.
- Rules, docs and skills work at once. Scripts, hooks and MCP servers run only for packages you trust. Trusting `@acme/ui` does not trust `@acme/colors`.
- `"pin"` keeps a new version's tools off until you run `npx harnesspm approve`.
- When an agent runs harnesspm, new hooks, MCP servers and allow rules wait until a person reviews and merges them.
- Rules are instructions to your agent. Review their changes in the pull request, like code.

`why` shows where any unit comes from and every change made to it. Here, the colors rule has a patch from `@acme/ui` and the app's own:

<Terminal command="npx harnesspm why acme-colors:rules/usage" output={whyColorsUsage} fields />

Agents run the same command. The `harnesspm-improve` skill takes them from `why` to a change saved the way the unit's owner asks.

## Bring your own rules to every repository

Your team's and your own way of working can follow you into every repository, without a commit. `add` puts a harness on top of the repository's, on your machine:

```shell
npx -y @tenphi/harnesspm add \
  github:<owner>/<repo>
```

It applies in every repository on your machine, and one line in a setup script brings it to Claude Code cloud sessions. `npx harnesspm doctor` checks that its files stay out of git. [Bring your own harness](/bring-your-own) shows how to start one.

## In real projects

These projects ship a harness. Read them as working examples:

- [Glaze](https://github.com/tenphi/glaze), a color toolkit: a rule, docs, a skill and scripts.
- [Tasty](https://github.com/tenphi/tasty), a styling library: a rule, docs and a script.
- [eslint-plugin-tasty](https://www.npmjs.com/package/@tenphi/eslint-plugin-tasty), the lint plugin for Tasty: a rule, docs, a script and a hook.
- [Cube UI Kit](https://github.com/cube-js/cube-ui-kit/pull/1643), a design system that passes on all three. Its harness is a pull request for now.
- [harnesspm](https://github.com/tenphi/harnesspm/tree/main/harness) itself: two rules, three skills and the specification as docs.

harnesspm started with these packages. The [motivating case](https://github.com/tenphi/harnesspm/blob/main/docs/research/motivating-case.md) shows the manual work it replaced there. In [a recorded run](https://github.com/tenphi/harnesspm/blob/main/docs/research/agent-capabilities.md#claude-code), Claude Code used UI Kit's docs and tools for a task that named none of them.
