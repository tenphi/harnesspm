Run these once in a project. `init` makes every install run `harnesspm sync`, which updates what your agents read.

## Your agent doesn't know your libraries

Without help, an agent in your project guesses how your libraries work, or it remembers an older version. Today the fix is manual:

- Teams paste rules into `AGENTS.md`, and the rules drift away from the code.
- A library can put docs in its package, but nothing points the agent at them.
- Each agent reads its own files: `CLAUDE.md` and `.claude/` for Claude Code, `.codex/` for Codex.
- A library that builds on another one copies the upstream rules, and the copies go stale.

[A real chain of packages](../docs/research/motivating-case.md) shows each of these problems.

## How it works

A library writes its harness once, and every project that installs the library gets it.

## What your agent sees

Your agent gets short, current instructions, and you can trace each one to its source. Our example is an app on Cube UI Kit, a React design system built on Glaze (colors) and Tasty (styles). UI Kit's harness is on a branch and not published yet; this is real output from that branch.

Each rule, docs index or script is a **unit** with an ID, such as `glaze:rules/colors`. The managed block that harnesspm writes into `AGENTS.md` names the unit behind every line:

<ManagedBlock marks={{ '#### Where colors come from': 'patched by uikit' }} />

The app depends only on UI Kit. Glaze comes through UI Kit, and UI Kit's patch rewrites the first section of Glaze's rule for apps on UI Kit. Lines marked `…` are cut here.

Docs are one pointer line each, and skills load when needed, so the always-on text stays small. `npx harnesspm status` shows its size.

## Your agent uses it

A harness changes what the agent does, not only what it reads. In one headless Claude Code run, in a fresh app on that UI Kit branch, the task was: *"Create src/components/StatusBadge.tsx: a small pill that shows a status ('ok', 'warning' or 'error') with a matching color, slightly darker on hover…"* It did not mention harnesspm or the tools. In 12 turns, the agent:

1. read UI Kit's docs and Usage guide, and built a `tasty()` component instead of restyling the protected `Badge` and `Tag`;
2. picked palette pairs and checked their contrast with `uikit:tokens`;
3. read Tasty's `dsl.md` from Tasty's own docs index;
4. checked its CSS with `tasty:styles --setup @cube-dev/ui-kit/dist/components/Root.js`.

Source: the [UI Kit pull request](https://github.com/cube-js/cube-ui-kit/pull/1643), recorded in [agent capabilities](../docs/research/agent-capabilities.md#claude-code).

## Upgrade the package, upgrade the rules

Your agent's knowledge of a library updates when the library does. Rules, docs and tools come from the version in `node_modules`. Nothing is copied, so nothing drifts. The managed block and the lock are committed, so the pull request shows what changed. Here, Tasty 3.19.1 changed its `styles` script:

## Libraries pass on what they build on

A library gives your agent the harness of the libraries under it too, adapted to itself. An app that installs UI Kit gets:

- `@cube-dev/ui-kit`: its rule, its component docs and `uikit:tokens`
  - `@tenphi/glaze`: its colors rule, patched by UI Kit, its docs, the `glaze-theme` skill and three scripts
  - `@tenphi/tasty`: its styles rule, patched by UI Kit, its docs and `tasty:styles`
  - `@tenphi/eslint-plugin-tasty`: its lint rule, its docs, `tasty-lint:check` and a hook

The lint plugin is an optional peer of UI Kit, so its harness applies only when the app installs the plugin. Each package comes in the version that UI Kit uses. This is the core of UI Kit's manifest:

## One source for Claude Code and Codex

You keep one copy of each instruction, not one per agent. Write a rule, skill, sub-agent or hook once. Each agent gets it in its own files: the managed block in `AGENTS.md` for both, `.claude/` for Claude Code, `.codex/` and `.agents/skills/` for Codex. See [every file harnesspm writes](../docs/spec/04-outputs.md).

This works before any library ships a harness:

- **Your project.** `npx harnesspm new rule usage` starts a `harness/` folder in your repository.
- **All your repositories.** Publish shared rules as a harness-only package, and add it as a dev dependency in each.

## You decide what applies and what runs

Your project has the last word on every unit. One `harnesspm.json` holds your changes and your trust:

```json
{
  "$schema": "https://unpkg.com/@tenphi/harnesspm/schema/harnesspm.schema.json",
  "patch": {
    "glaze:rules/colors": "./harnesspm/patches/glaze-colors.patch.md"
  },
  "exclude": ["tasty-lint:hooks/check-edit"],
  "trust": {
    "@cube-dev/ui-kit": true,
    "@tenphi/tasty": true,
    "@tenphi/eslint-plugin-tasty": true,
    "@tenphi/glaze": "pin"
  }
}
```

- A **patch** changes one section of a rule and keeps the rest. When an upgrade changes that section, `sync` warns you. **exclude** drops a unit or a whole package. **replace** swaps a unit for your own file.
- Rules, docs and skills work at once. Scripts, hooks and MCP servers run only for packages you trust. Trusting UI Kit does not trust Tasty.
- `"pin"` keeps a new version's tools off until you run `npx harnesspm approve`.
- When an agent runs harnesspm, new hooks, MCP servers and allow rules wait for a person.
- Rules are instructions to your agent. Review their changes in the pull request, like code.

`why` shows where any unit comes from and every change made to it. In the UI Kit app, Glaze's rule has UI Kit's patch and the app's own:

<Terminal command="npx harnesspm why glaze:rules/colors" output={whyGlazeColors} fields />

Agents run the same command. The `harnesspm-improve` skill takes them from `why` to a change saved the way the unit's owner asks.

## Bring your own rules to every repository

Your team's and your own way of working can follow you into every repository, without a commit. `add` puts a harness on top of the repository's, on your machine:

```shell
npx -y @tenphi/harnesspm add \
  github:<owner>/<repo>
```

It applies in every repository on your machine, and one line in a setup script brings it to Claude Code cloud sessions. `npx harnesspm doctor` checks that its files stay out of git.

## Scope today

- harnesspm is before 1.0. Formats and commands can still change.
- It writes files for Claude Code and Codex first. Other agents that read `AGENTS.md` and `.agents/skills/` get the portable parts.
- It runs on a person's computer and in Claude Code cloud sessions. Codex Cloud is not supported yet.
- It works with npm, pnpm, Yarn 1, and Yarn 4 with the `node-modules` linker, on Node.js 20 or later.
- Packages with a harness on npm today: `@tenphi/glaze`, `@tenphi/tasty`, `@tenphi/eslint-plugin-tasty` and `@tenphi/harnesspm`. UI Kit's harness, in the examples above, is not published yet.
