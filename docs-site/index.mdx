Run these once in a project. `init` creates `harnesspm.json`, runs `harnesspm sync` after every install and makes `CLAUDE.md` import `AGENTS.md`. From then on, every install keeps your agents current.

## Your agent doesn't know your libraries

An agent in your project doesn't know how your libraries should be used, or it knows an older version. Today that knowledge travels by hand:

- Teams paste rules into `AGENTS.md`, and the rules drift away from the code.
- Every agent wants its own files: `CLAUDE.md`, `.claude/`, `.codex/`.
- A library author has no way to ship guidance with the package.
- A library that builds on another one copies the upstream rules, and the copies go stale.

[A real chain of packages](../docs/research/motivating-case.md) shows each of these problems.

## How it works

A library writes its harness once, and every project that installs it gets it.

## One harness, every agent

You write a unit once, and each agent gets it in its own native format. The `harness/` folder is an [Agent Plugins 1.0](https://agent-plugins.org/) plugin, with skills in the [Agent Skills](https://agentskills.io/specification) format.

| In `harness/` | Claude Code | Codex |
| --- | --- | --- |
| Always-on rules, docs index, scripts | `AGENTS.md` block, through `@AGENTS.md` in `CLAUDE.md` | `AGENTS.md` block |
| File-scoped rules | `.claude/rules/`, active on matching files | A pointer line in the block |
| Skills | `.claude/skills/` | `.agents/skills/` |
| Sub-agents | `.claude/agents/` | `.codex/agents/` |
| Hooks and permissions | `.claude/settings.local.json` | `.codex/hooks.json`, `.codex/rules/` |
| MCP servers | `~/.claude.json`, for this project | `.codex/config.toml` |

Other agents that read `AGENTS.md` and `.agents/skills/` get the portable parts. See [what harnesspm writes](../docs/spec/04-outputs.md) for every file.

## Composes like dependencies

A library passes on the harness of the libraries it builds on (`extends`) and adapts it for its users (`patch`). An app that installs Cube UI Kit gets this:

UI Kit adapts the Glaze and Tasty rules to its own palette and setup. The Tasty lint plugin is an optional peer of UI Kit, so its harness comes only when the app installs the plugin. Each package arrives in the version that UI Kit uses.

## Yours to adjust

You can change any unit from any package without forking it. Patch one section of a rule, or replace or exclude a whole unit, in `harnesspm.json`:

```json
{
  "patch": { "glaze:rules/colors": "./harnesspm/patches/glaze-colors.patch.md" },
  "exclude": ["@tenphi/eslint-plugin-tasty"]
}
```

`npx harnesspm why <ID>` says where any line came from and how to change it:

```text
$ npx harnesspm why glaze:rules/colors
owner       dependency @tenphi/glaze 3.1.0
source      node_modules/.harnesspm/pkgs/@tenphi/glaze/harness/dev.harnesspm/rules/colors.md
patch       harnesspm/patches/glaze-colors.patch.md (from harnesspm.json)
repository  https://github.com/tenphi/glaze
editable    no. Add a `patch`, `replace` or `exclude` in harnesspm.json, or propose the change upstream.
```

Agents use the same command. harnesspm's own `harnesspm-improve` skill walks them from `why` to a change that the unit's owner accepts.

## Safe by default

Text needs no permission, and anything that runs code waits for yours.

- Scripts, hooks and MCP servers run only for packages that your project trusts in `harnesspm.json`.
- Trust never passes through `extends`: trusting UI Kit does not trust Tasty.
- An agent cannot grant itself permissions. New allow rules, hooks and MCP servers from a run the agent started wait for a person.
- `npx harnesspm sync --check` in CI fails when the block or the lock is out of date.

```json
{
  "trust": {
    "@cube-dev/ui-kit": true,
    "@tenphi/glaze": "pin"
  }
}
```

`true` follows upgrades. `"pin"` keeps a package at the version you approved until you run `npx harnesspm approve`.

## A layer of your own

Bring your team's or your own rules, notes and skills to every repository, without committing them:

```shell
npx -y @tenphi/harnesspm add github:<owner>/<repo>
```

An added harness applies on top of the repository's, in every repository on your machine. One line in a setup script brings it to Claude Code cloud sessions. Its files stay out of git, and `doctor` checks that they do:

```text
$ npx harnesspm doctor
🔒 Local files
  ✅ 12 per-machine files: ignored by git and not tracked
➕ Harnesses of your own
  ✅ .git/info/exclude can be written, so harnesspm keeps per-machine files out of git
  ✅ Added: alex (github:alex/harness, user)
📦 Outputs
  ✅ Committed outputs are up to date
  ✅ 14 per-machine outputs in place

✅ Ready. Nothing to fix.
```

## Small, focused context

Always-on text costs context in every session, so harnesspm keeps it short and tells you its size. Docs and on-demand rules are one pointer line each, and skills load when they are needed. `npx harnesspm status` reports the always-on size for each agent:

```text
📏 always-on     Codex 3.1 KiB of 32 KiB · Claude Code 51 lines
```

A team that wants to see how agents use its harness can turn on [telemetry](../docs/guide/telemetry.md). It is off by default, and events go only to the team's own handler.

## Scope today

- harnesspm is before 1.0. Formats and commands can still change.
- It writes files for Claude Code and Codex first. Other agents that read `AGENTS.md` and `.agents/skills/` get the portable parts.
- It runs on a person's computer and in Claude Code cloud sessions. Codex Cloud is not supported yet.
- It works with npm, pnpm, Yarn 1, and Yarn 4 with the `node-modules` linker, on Node.js 20 or later.
