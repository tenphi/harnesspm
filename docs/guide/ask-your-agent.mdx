title: Ask your agent
description: Prompts for the common harnesspm tasks, what your agent does with each, and the decisions that stay with you.
---

**In short**

- These prompts work in a repository where `npx -y @harnesspm/cli init` has run: after [Get started](./setup.md), or in a library after [See what your users get](./share.md#see-what-your-users-get). Your agent then has three skills for harnesspm.
- Each task below has a prompt, what your agent does, and what you decide.
- The tasks that start with harnesspm have a one-line prompt in their guides: [Get started](./setup.md), [Share a harness from your library](./share.md) and [Add your own or your team's harness](./add-your-own.md). Each names the command that starts the task, and the command prints the steps.

The prompts are examples. Use your own words, and your own package names in place of `@acme/ui`. Keep the word harnesspm in each prompt: it tells your agent which tool and which skill to use.

## See what you got, and check the setup

```text
Run `npx -y @harnesspm/cli` and tell me what it reports.
```

- **Your agent** lists the packages with a harness, the size of the always-on text, the checks that per-machine files stay out of git, and what waits for you. The command changes nothing, and each problem names the command that fixes it.
- **You** learn what your agent now knows. Each rule in `AGENTS.md` ends with an ID that names its source.
- **You decide** on any fix that changes what git tracks.

## Turn on a package's tools

```text
Trust @acme/ui in harnesspm.
```

- **Your agent** adds the package to `trust` in `harnesspm.json` and runs `npx -y @harnesspm/cli sync`.
- **You** run `npx -y @harnesspm/cli approve` in your own terminal. Until then, new hooks, MCP servers and allow rules wait.
- **You decide** how far the trust goes: `true` follows upgrades, and `"pin"` asks again for each new version. Use `"pin"` for packages your team does not control. See [Trust and safety](./trust.md).

## Fix a rule that does not fit

```text
The contrast rule from @acme/colors is too weak for us:
we target WCAG AAA. Change it for this project
with harnesspm.
```

- **Your agent** finds the rule's source with `npx -y @harnesspm/cli why`, and adds a patch that changes one section and keeps the rest.
- **You** review the change to `AGENTS.md` in the pull request.
- When a rule is wrong for everyone, also ask: "Propose this change to the package." See [Change upstream units](./change-upstream.md).

## Remember something

```text
Remember this in our harnesspm harness:
we use Conventional Commits in this repository.
```

- **Your agent** writes a rule into the project's harness. When the note is about how you work everywhere, it goes into your own harness. Without the word harnesspm, an agent may keep the note in its own memory, where your team never sees it.
- **You decide** where it belongs, when your agent asks. A project rule reaches the whole team, so it comes as a normal change to review.

## Add your own harness to every repository

Your own rules, notes and skills can live in a repository of yours, and apply on top of any project. [Add your own or your team's harness](./add-your-own.md#ask-your-agent) has the prompt that starts one, and what stays with you: you add it in your own terminal, because adding a harness is your trust decision.
